# doorman v0.5 brainstorm: per-app policies

Status: partially implemented (2026-10-24). The proxy-username profile
selection and additive `/etc/doorman/apps/<app>.txt` files are in place; the
`.pending` learn flow and cgroup enforcement below are still future work.

## Problem

Today the strict proxy has one global allowlist for every non-browser process.
That makes discovery painful and over-broad: a host added for Steam is also
reachable by every other app, and Steam Cloud needs regional bucket hosts that
change over time.

## Why not use Referer for apps?

- TLS hides the header. `strict_proxy.py` only reads the SNI; it does not MITM.
- Many apps never send `Referer` (native clients, updaters, APIs, CDNs).
- `Referer` is attacker-controlled. Any process can forge
  `Referer: https://steamcommunity.com`.

`Referer` works in the browser addon because it already MITMs and because the
policy there is "an allowlisted page may load its own assets". It is a
convenience, not a security boundary.

## "Allow the .exe" is really "allow the process"

The kernel does not apply network policy by binary path. It identifies
processes by UID, cgroup, network namespace, or LSM label.

| Mechanism | Identity | Hostname-aware? |
|---|---|---|
| `doorman-run` + env proxy | voluntary | yes, via proxy |
| nftables `meta skuid` | UID | no, IP/port only |
| nftables `socket cgroupv2` | cgroup | no, IP/port only |
| per-app proxy + proxy auth | app credential | yes |
| network namespace per app | namespace | yes, if routed through a proxy |
| AppArmor/SELinux network rules | profile | port-level, not hostname |
| eBPF on `connect()` | process | yes, with DNS correlation |

Hostname policy wants a proxy. Process policy wants cgroups/UIDs. The clean
design combines them: force the process through a proxy that knows which
profile it belongs to.

## Proposed design: per-app profiles

Profiles live under `/etc/doorman/apps/`:

```
/etc/doorman/apps/steam.txt
/etc/doorman/apps/steam.pending     # DENY hosts collected in learn mode
/etc/doorman/apps/obsidian.txt
```

`doorman-run steam` would:

1. Start (or select) a proxy instance with Steam's profile.
2. Export a proxy URL carrying a per-app credential, for example
   `http://steam:<token>@127.0.0.1:8081`.
3. The proxy reads `Proxy-Authorization`, maps the username to
   `apps/<name>.txt`, and adds that list to the global allowlist.
4. nftables places the app in a cgroup and allows it to reach only its proxy
   port plus DNS; direct traffic is dropped.

One listener can serve many profiles this way. For stronger isolation, use
separate proxy ports or separate UIDs so one app cannot use another's profile.

## Enforcement options

- **cgroup per app** — `doorman-run` launches the app in a systemd scope or
  slice, and nftables matches `socket cgroupv2`. This is the most practical
  option for GUI apps.
- **separate UID per app** — simplest nftables matching (`meta skuid`), but
  painful for GUI apps: display, audio, and home-directory access.
- **network namespace per app** — strongest isolation; every packet must leave
  through a veth and a policy proxy. Significant setup complexity.
- **per-app proxy port** — easy to implement, but same-UID apps can reach the
  port unless cgroup rules restrict it.

## Discovery should be a command

Manual journal reading does not scale:

```bash
journalctl -u doorman-strict --since "1 hour ago" -o cat \
  | awk '$1=="DENY" {print $2}' | sort -u
```

Proposed commands:

```bash
doorman-run --learn steam       # start in dry-run, collect DENY hosts
doorman-allow steam --pending   # append pending hosts to steam.txt, reload
doorman-allow steam HOST        # add one host explicitly
```

`--learn` is today's `--dry-run`, but it writes structured `DENY` lines into the
app's pending profile instead of making the user eyeball the journal.

## Steam Cloud and glob patterns

Steam Cloud uses regional third-party buckets, for example:

```
steamcloud-eu-ams.storage.googleapis.com
steamcloudfrankfurt.blob.core.windows.net
steamcloud-frf.s3.dualstack.eu-central-1.amazonaws.com
```

Glob entries collapse these into a few lines:

```
steamcloud-*.storage.googleapis.com
steamcloud*.blob.core.windows.net
steamcloud-*.s3.*.amazonaws.com
steamcloud-*.s3.amazonaws.com
```

Globs in a global allowlist are broad: every app can use any matching bucket.
Per-app profiles scope the same patterns to Steam only. For the strictest
policy, keep exact hosts and use `--learn` to collect new ones.

## The overlay browser caveat

`steamwebhelper` is a child of Steam. Under a per-app cgroup it inherits
Steam's profile, so the overlay can reach Steam hosts but nothing else.

Fully blocking the overlay requires either:

- moving `steamwebhelper` into a stricter cgroup after it starts, or
- MITM with URL/path filtering, which brings CA trust and pinning problems.

This is why the overlay remains a special case rather than a solved problem.

## Threat model

- Same-UID processes can usually read each other's environment
  (`/proc/<pid>/environ`), so proxy credentials are a convenience, not a hard
  boundary. cgroups and separate UIDs are enforcement.
- Root is exempt from the UID firewall. `--remove-wheel` is the step that closes
  the normal sudo/pacman bypass.
- Glob patterns widen access for every app sharing the profile.

## Suggested order

1. Per-app profile files plus proxy-auth selection.
2. `--learn` and `doorman-allow` commands.
3. cgroup-based nftables enforcement.
4. Separate UID or network namespace per app, only if hard isolation is needed.

## Open questions

- How to assign GUI apps to cgroups without breaking display/audio/home access?
- Which nftables/cgroup syntax and kernel versions to require?
- How to identify and isolate children such as `steamwebhelper` reliably?
- Profile reload semantics: restart the proxy, or reload on SIGHUP?
- Proxy auth over CONNECT and plain HTTP; transparent redirect has no auth
  header and would need a different mapping.
